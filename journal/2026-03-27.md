## Multi-Level Cache (Local + Distributed)

### Architecture

`MultiLevelCache` is a two-layer `Cache` implementation: a local
Caffeine layer in front of a distributed Redis layer. Read path:

```
get(key)
  1. check local (Caffeine)  → hit: return immediately
  2. check distributed (Redis) → hit: populate local, return
  3. miss: return null → @Cacheable calls the real method → put()
```

Write path always writes distributed first, then local — ensures the
distributed layer is the source of truth.

`MultiLevelCacheManager` builds one `MultiLevelCache` per registered
cache name by delegating to both `CaffeineBackedCacheManager` and
`RedisBackedCacheManager`.

### `putIfAbsent` not overridden

The default `Cache` interface implementation is a non-atomic
get-then-put. `RedisCache` overrides this with `SET NX` (atomic), but
coordinating the SET NX result back to the local Caffeine layer adds
complexity. Not overriding is acceptable when strict once-only writes
are not required. If needed: delegate to `distributedDelegate.putIfAbsent()`
and sync the result to local.

### Separate localTtl / distributedTtl

`CacheDefinition` holds two TTL fields — `localTtl` and `distributedTtl`
— instead of a single `ttl`. The local TTL is typically shorter to
bound stale reads. `CaffeineBackedCacheManager` always uses `getLocalTtl()`
regardless of cache type; `RedisCacheManager` always uses
`getDistributedTtl()`.

### CacheType.DISTRIBUTED_BACKED

`EnumSet.of(DISTRIBUTED, MULTI_LEVEL)` — used in `CacheConfig` to
filter which caches need Redis pre-population. Named for the
abstraction, not the implementation.

## Redis Trace Noise — Investigation & Outcome

### Problem

Redis command spans (SET, HELLO, CLIENT) appear as isolated root
traces in Jaeger — separate from the request that triggered them.

### Root causes (two distinct cases)

**Async cache writes (SET)**

When `RedisCacheManager.put()` is called and `LettuceConnectionFactory`
is used (which implements `ReactiveRedisConnectionFactory`), Spring
Data Redis dispatches the write via `AsynchronousCacheWriterDelegate`
onto a reactive scheduler thread. That thread has no trace context,
so the SET span starts with no parent.

GET is synchronous (must return a value) so it always runs on the
calling thread with full trace context — GET spans are fine.

**Connection handshake commands (HELLO, CLIENT)**

Lettuce sends these autonomously on its Netty IO threads during
connection setup, completely outside any application request. No
propagation strategy can attach these to a trace — they have no
originating request.

### What was tried

**Approach 1: `ObservationPredicate` filter**

Dropped `spring.data.redis` observations with no parent. Did not work
— Lettuce creates Redis command spans via its own native OTel
instrumentation, bypassing Micrometer's `ObservationRegistry` entirely.
`ObservationPredicate` never sees them.

The `otel.scope.name: org.springframework.boot` attribute on the span
is misleading here — it reflects the OTel instrumentation scope name,
not that the span went through Micrometer's `ObservationRegistry`.

**Approach 2: Reactor context propagation**

Added `io.micrometer:context-propagation` + called
`Hooks.enableAutomaticContextPropagation()` on startup. Did not work.

`Hooks.enableAutomaticContextPropagation()` propagates thread-local
context across Reactor scheduler boundaries. But the actual Redis SET
command executes on Lettuce's **Netty IO thread**, which is outside
Reactor's scheduler machinery entirely — the hook never fires there.
Additionally, HELLO/CLIENT commands have no originating application
context at all regardless of propagation strategy.

**Approach 3: OTel `Sampler` bean**

A `Sampler` is called for every span at creation time, regardless of
whether it comes from Micrometer or native OTel instrumentation — the
correct interception point. Condition: `SpanKind.CLIENT` + no valid
parent context.

Could not be wired in: `SdkTracerProviderBuilderCustomizer` (the
Spring Boot 3.x customizer hook) does not exist in Spring Boot 4.
Alternative API not found in time.

### Outcome

Accepted the orphaned Redis spans as trace noise. The `multiLevelDynamic`
cache type avoids the async write issue entirely — it routes through
`RedisExpirableCache.put()` → `RedisTemplate.opsForValue().set()` which
is synchronous on the calling thread and traces correctly. The
`game-details` cache is set to `multiLevelDynamic` for this reason.

HELLO/CLIENT handshake spans cannot be resolved without the Sampler
approach.

### Key insight: ObservationPredicate vs Sampler

| | `ObservationPredicate` | OTel `Sampler` |
|---|---|---|
| Intercepts | Spans via Micrometer `ObservationRegistry` only | Every span, any origin |
| Use for | Spring MVC, Spring Data (when using Micrometer) | Library-native OTel (Lettuce, etc.) |
| Configured as | `@Component` | Via `SdkTracerProviderBuilderCustomizer` (Spring Boot 3) |

## multiLevelDynamic vs multiLevel — Tracing Difference

`multiLevel` (fixed TTL) → `RedisCache.put()` → `DefaultRedisCacheWriter`
→ async write → orphaned SET span in Jaeger.

`multiLevelDynamic` → `RedisExpirableCache.put()` → `RedisTemplate`
→ synchronous write → SET span correctly nested under the request trace.

This is why `game-details` uses `multiLevelDynamic` — the dynamic TTL
is read from `Expirable#cacheDuration()` on the value, giving per-entry
TTL control as a bonus.
