# 2026-03-25 — playground service

## Exception & Error Handling

**Final design:** `BaseErrorDecoder` wraps every failed Feign response into a
typed exception (`BadRequestException`, `NotFoundException`, etc.) with a
`FeignException` as the Java cause. `GlobalExceptionHandler` logs the clean
message plus the cause stack trace, and returns a JSON response with only
`status`, `message`, and a short `errorId` (8-char UUID prefix).

**Why this way:**
- Using `FeignException.errorStatus(methodKey, response)` as the cause
  (rather than a plain `RuntimeException(body)`) captures the full upstream
  context — status code, headers, body, and the Feign method name — without
  any custom fields on our exception classes.
- The caller-facing message (`"upstream not found"`, `"upstream access
  denied"`) is deliberately vague. The raw upstream body lives only in the
  cause, visible in server logs but never sent to the client.
- Passing the cause as the trailing SLF4J argument (not a `{}` placeholder)
  is how SLF4J prints stack traces. The cause's own message is included in
  that output, so there is no need to extract it manually — `causeMessage()`
  helper was removed for this reason.
- `errorId` lets us correlate a user-reported error directly to a log line
  without exposing any internal detail in the HTTP response.
- `NoResourceFoundException` is handled silently (no log, plain 404) because
  browsers and tooling (Chrome DevTools, favicon probes) generate these on
  every page load — they are not application errors.

## Cache

**Null result skipping:** `@Cacheable(unless = "#result == null")` on
`getGameDetails` — when Yahoo returns 404 the service returns null, and Spring
skips caching that result entirely. This is the right mechanism: the `unless`
SpEL expression is evaluated after the method returns, so a null simply
bypasses the cache store with no exception and no `NullValue` wrapper in
Caffeine.

**Why not `allowNullValues = false`:** Setting that on `CaffeineCache` throws
`IllegalArgumentException` on null — too aggressive. `unless` achieves the
intent (don't cache transient absences) without breaking the call.

**`CacheConfig` moved to `cache/` package:** It configures Caffeine caches
and depends on `Expirable` and `DiagnosticCache`, both in `cache/`. Keeping
it in `config/` was an arbitrary separation; moving it collapses the package
boundary to where the cohesion actually is.

## Spring Boot 4 Upgrade (3.5.4 → 4.0.4)

**Why upgrade:** Spring Boot 4 ships with Spring Framework 7, which includes
native API versioning support — the main motivation for this session.

**Key dependency changes and why:**
- `spring-boot-starter-web` → `spring-boot-starter-webmvc`: Boot 4
  modularised the web layer; the MVC-specific starter is now explicit.
- `micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp` →
  `spring-boot-starter-opentelemetry`: Boot 4 modularisation means the
  `Tracer` bean is no longer auto-configured by having the bridge on the
  classpath alone. The dedicated starter wires everything correctly. This
  was found empirically — context load failed with `NoSuchBeanDefinition:
  Tracer` until the starter was added.
- Spring Cloud `2025.0.0` → `2025.1.0` (Oakwood): the compatible release
  train for Boot 4.

**OTLP export disabled by default** (`management.otlp.metrics.export.enabled`,
`management.otlp.tracing.export.enabled`): the starter configures an OTLP
exporter that pushes to `localhost:4318` by default. No collector runs in dev,
causing noisy `Connection refused` warnings every publish interval. Tracing
(traceId/spanId in logs) is unaffected — that is in-process and does not
require a collector.

## API Versioning (Spring Framework 7)

**Final setup:**
- `WebMvcConfig` calls `configurer.usePathSegment(1)` — version is at index 1
  in `/api/{version}/resource`.
- All controllers use `@RequestMapping("/api/{version}/resource")` with
  `@GetMapping(version = "1+")` on each method.
- No `server.servlet.context-path` — not needed and it interfered with how
  the path segment index is resolved.

**Why `{version}` must be in `@RequestMapping`:**
Spring's path-based versioning does **not** strip the version segment before
handler mapping. It reads the segment to determine which method to invoke, but
the full URL — including the version segment — is still used to match the
controller. Without `{version}` in the path, the handler mapping finds no
match and the request falls through to the static resource handler (resulting
in a silent 404).

**Why `usePathSegment(1)` not `(0)`:**
The index is relative to the full request URL, not any context path. In
`/api/v1/echo`, `api` is segment 0 and `v1` is segment 1. The Javadoc
example makes this explicit: "for `/api/{version}/...` use index 1."

**Why `"v1"` works without custom parser configuration:**
`SemanticApiVersionParser` is the default (confirmed in source:
`ApiVersionConfigurer.getApiVersionStrategy()` falls back to
`new SemanticApiVersionParser()` when none is set). It internally calls
`skipNonDigits()` before parsing, so `"v1"` → `1` automatically.

**Version range semantics:**
- `"1+"` — version 1 and any higher version that has no more specific handler.
- Adding `"5"` (or `"5+"`) later creates a more specific handler for that
  version range; `"1+"` continues to cover v1–v4.
- A request with no version returns 400 (`MissingApiVersionException`)
  automatically — no handler needed in `GlobalExceptionHandler`.

## HTTP Client: Feign → Spring @HttpExchange + JDK HttpClient

**Replaced Feign with Spring Framework 7's native `@HttpExchange` interfaces**
backed by `RestClient` and JDK `HttpClient` as the transport layer.

**Why replace Feign:**
- Feign is a third-party library (OpenFeign); Spring Framework 7 ships a
  first-class equivalent via `@HttpExchange` + `RestClient` — no extra
  dependency.
- JDK `HttpClient` (Java 11+, built into the JDK) supports HTTP/2 natively.
  Feign's default transport (Apache HttpClient or OkHttp) requires extra config
  to support HTTP/2. With `HttpClient.Version.HTTP_2`, the JVM negotiates h2
  via ALPN on TLS automatically, falling back to HTTP/1.1 if the server doesn't
  support it.

**Wire-up pattern per client:**
```
RestClient.builder()
  .baseUrl(...)
  .requestFactory(JdkClientHttpRequestFactory)   // JDK transport
  .observationRegistry(...)                       // tracing
  .requestInterceptor(...)                        // params, logging
  .defaultStatusHandler(...)                      // error mapping
  → HttpServiceProxyFactory → @HttpExchange proxy
```

## ClientStatusHandlers

Maps upstream HTTP error status codes to typed application exceptions
(`BadRequestException`, `NotFoundException`, `ForbiddenException`, etc.) with
the raw `RestClientResponseException` as the Java cause. `GlobalExceptionHandler`
then converts these to clean API responses.

**Why store raw cause:** captures upstream status, headers, and body for server
logs without exposing them in the API response.

## QueryParamInterceptor

A `ClientHttpRequestInterceptor` that appends query parameters to every
outbound request. Uses static factory methods instead of public constructors:

- `build(params)` — fixed key/value params (e.g. `source=playground`)
- `onlyApiKey(paramName, secretName, env, filePath, gcpProjectId)` — loads an
  API key once at startup; from a local JSON file in dev, from GCP Secret
  Manager in stage/prod
- `withApiKey(params, ...)` — combines fixed params and an API key

**Why static factories:** hides the loading logic; callers don't need to know
which constructor path is taken based on the active profile.

## LoggingInterceptor

A `ClientHttpRequestInterceptor` that logs every outbound request
(`METHOD url`) before execution. Registered after `QueryParamInterceptor` so
the fully-built URI (including appended params) is what gets logged.

Accepts a `Set<String>` of param names to redact — their values are replaced
with `***` in the log output. Each client config declares its own redact list:

- Google Pollen: `Set.of("key")` — API key param hidden
- Yahoo Sports / Ambee: `noRedaction()` — no sensitive params in the URL

**Why not rely on JDK HttpClient logging:** the JDK transport logs at the
system/JUL level, difficult to control format, and exposes raw API keys in the
URL. `LoggingInterceptor` gives structured, masked output via SLF4J.

## Yahoo Sports: JDK Dynamic Proxy to Swallow 404

`SportService` calls `YahooSportsClient` for team/game lookups. Yahoo returns
404 when a team or game ID is not found — this is expected and should return
`null` to the caller, not throw an exception.

**Problem:** `@HttpExchange` interfaces can't return `null` for error responses
directly — the status handler must throw for the body parser to skip, and
try/catch in every service method doesn't scale.

**Solution:** wrap the `@HttpExchange` proxy in a JDK dynamic proxy
(`Proxy.newProxyInstance`) registered as the `YahooSportsClient` bean. The
proxy catches `NotFoundException` (thrown by `ClientStatusHandlers` for 404),
logs a warning, and returns `null`. All current and future methods on the
interface are covered automatically — no changes needed as the interface grows.

```
Spring injects → JDK proxy (catches 404 → null)
                    → @HttpExchange proxy (makes HTTP call)
                        → RestClient → JDK HttpClient → Yahoo
```

`SportService` was simplified: no try/catch blocks, just null-checks on the
returned value.

## Redis / Valkey L2 Cache (Design Discussion, Not Yet Implemented)

**Why L2:** Caffeine is in-process — each pod has its own cache. A Redis/Valkey
L2 cache is shared across pods, so a cache warm on one pod benefits all others.

**Connection desync in Lettuce:**
Lettuce (Spring Boot's default Redis client) multiplexes many threads over a
single TCP connection per node using a command pipeline. Commands and responses
are matched in FIFO order. If a timeout or partial read disrupts this ordering,
every subsequent command on that connection gets the wrong response — this is a
desync. Lettuce detects it, resets (closes and reopens) the connection, and
all in-flight commands on that connection fail with an exception.

Our application layer should catch these exceptions and treat them as cache
misses (fall through to the upstream API) rather than letting them surface as
500s. The cache is not the source of truth.

**Cluster routing and `MOVED`:**
In cluster mode, the client computes `CRC16(key) % 16384` to route each
command to the correct node directly — no proxy. When data moves after a
reshard, the target node returns `MOVED <slot> <host:port>`. Lettuce follows
the redirect automatically, but topology refresh
(`ClusterTopologyRefreshOptions`) should be enabled so Lettuce proactively
updates its slot map rather than relying solely on reactive corrections.

**Valkey over Redis:**
Valkey is a Redis-compatible fork under the Linux Foundation (BSD licence),
created after Redis relicensed in 2024. GCP Memorystore supports it. It is a
drop-in replacement — same protocol, same Lettuce client, same Spring Data
Redis API. Prefer Valkey for new deployments to avoid licence risk.
