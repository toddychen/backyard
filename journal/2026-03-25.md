# 2026-03-25 — playground service

## Distributed Tracing: Jaeger Setup & Upgrade

### Deploying Jaeger to Kind

Deployed Jaeger to a dedicated `observability` namespace in the Kind cluster
using a custom Helm chart (`infra/helm/jaeger/`). Key setup decisions:

- **Image:** started with `jaegertracing/all-in-one:1.76.0` (v1), later
  upgraded to `jaegertracing/jaeger:2.16.0` (v2, see below)
- **In-memory storage:** sufficient for local dev — traces are ephemeral,
  no persistence needed
- **NodePort 30686** for the UI, mapped via Kind `extraPortMappings` so
  the browser can reach `http://127.0.0.1:30686`
- **OTLP HTTP on port 4318** as ClusterIP only — playground pods reach it
  at `http://jaeger.observability:4318/v1/traces` via in-cluster DNS

**Why no OTLP NodePort for 4318/4317:** those ports only need to be reachable
from inside the cluster (playground → Jaeger). A ClusterIP is sufficient.
NodePort is only needed for the UI (host browser → cluster).

### Playground Tracing Config

- `management.tracing.sampling.probability=1.0` — 100% sampling in dev
  (default is 10%; most requests were invisible in Jaeger until this was set)
- `management.opentelemetry.tracing.export.enabled=true` in `application-dev.properties`
- `management.opentelemetry.tracing.export.otlp.endpoint` points at
  `http://localhost:4318/v1/traces` locally; overridden by
  `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT` env var in Kind
  to `http://jaeger.observability:4318/v1/traces`
- `spring.application.name=playground` in `application.properties` — sets
  the service name in Jaeger (without this, traces appeared under
  `unknown_service`)

**Correct Boot 4 property namespace:** `management.opentelemetry.tracing.*`
(not `management.otlp.tracing.*` which is the Boot 3 name). Both exist and
look plausible; the Boot 4 starter uses the `opentelemetry` namespace.

### Filtering Actuator Noise

Kubernetes liveness/readiness probes hit `/actuator/health/**` every few
seconds, flooding Jaeger with low-value traces.

**`management.tracing.web.skip-pattern` did not work** — investigated,
confirmed broken/removed in Boot 4.

**Working solution:** `ActuatorObservationFilter` implements
`ObservationPredicate` (`@Component`). Micrometer calls `test()` before
creating any span; returning `false` suppresses the observation entirely.
This is cleaner than sampler-based filtering which still creates a span
before discarding it.

```java
@Component
public class ActuatorObservationFilter implements ObservationPredicate {
    @Override
    public boolean test(String name, Observation.Context context) {
        if (context instanceof ServerRequestObservationContext ctx) {
            return !ctx.getCarrier().getRequestURI().startsWith("/actuator");
        }
        return true;
    }
}
```

No explicit registration needed — Spring Boot auto-detects all
`ObservationPredicate` beans and applies them.

### Upgrading to Jaeger v2

**Motivation:** Jaeger v1's dark theme was broken (suspected macOS-related
CSS issue). Jaeger v2 re-enabled dark mode by default in v2.14.0.

**Key changes in v2:**
- Image: `jaegertracing/all-in-one` (EOL, frozen at 1.76.0) →
  `jaegertracing/jaeger` (v2, single binary, same all-in-one behaviour)
- Config model: env vars replaced by an OTel Collector-style YAML file.
  For in-memory dev use, no config file is needed — defaults cover it.
- OTLP is on by default in v2; `COLLECTOR_OTLP_ENABLED=true` env var
  (required in v1) was removed.

**Helm chart changes to upgrade:**
- `values.yaml`: `repository: jaegertracing/jaeger`, `tag: "2.16.0"`
- `Chart.yaml`: `appVersion: "2.16.0"`
- `deployment.yaml`: removed `COLLECTOR_OTLP_ENABLED` env block

All ports (16686 UI, 4318 OTLP HTTP, 4317 OTLP gRPC) and NodePort
mappings stayed the same — no changes needed to the service or Kind config.

Confirmed running version via:
```
kubectl get pod -n observability <pod> \
  -o jsonpath='{.spec.containers[0].image}'
# → jaegertracing/jaeger:2.16.0
```

## Parallel Outbound Calls with Virtual Threads

### Fan-out Pattern

`getTeamGames` was extended to enrich each game from the team list by calling
`yahooSportsClient.getGameDetails(gameId)` per game — one outbound HTTP call
per game, sequential. A parallel variant `getTeamGamesParallel` was added,
exposed via the same endpoint with a `?parallel=true` query param:

```
GET /api/v1/sport/team/{teamId}/games           — sequential
GET /api/v1/sport/team/{teamId}/games?parallel=true — parallel
```

Both return the same `List<Game>` response; the difference is execution
strategy. Keeping one endpoint with a flag reflects that it is the same
resource, just fetched differently.

### Virtual Threads

Java 21 `Executors.newVirtualThreadPerTaskExecutor()` — each `getGameDetails`
call runs on its own virtual thread. All tasks start at the same time; the
calling thread blocks on `Future.get()` until each completes.

**Why virtual threads over `CompletableFuture` + thread pool:**
- No pool sizing — the JVM schedules virtual threads onto carrier threads
  automatically
- Blocking I/O (waiting for HTTP response) parks the virtual thread cheaply
  instead of tying up a platform thread
- Code stays imperative and readable — no chaining, no `thenApply`

**Why not `parallelStream()`:** uses the shared fork-join pool, which is
designed for CPU-bound work. Blocking I/O calls on it can starve other
work in the JVM.

### Trace Context Propagation Across Virtual Threads

**Problem:** trace context (active span, MDC) is stored in `ThreadLocal`.
When a task is submitted to a new virtual thread, the parent's `ThreadLocal`
values are not copied. Child spans created on virtual threads appear as
disconnected root spans in Jaeger — no link to the parent request span.

**Solution:** `ContextExecutorService.wrap()` from Micrometer's
`context-propagation` library. It wraps the executor so that every
`submit()` automatically captures the current context on the calling thread
and restores it on the virtual thread before the task runs.

```java
// ContextSnapshotFactory built once as a field (stateless, reusable)
private final ContextSnapshotFactory contextSnapshotFactory =
        ContextSnapshotFactory.builder().build();

try (ExecutorService executor = ContextExecutorService.wrap(
        Executors.newVirtualThreadPerTaskExecutor(),
        contextSnapshotFactory::captureAll)) {
    // all submit() calls automatically propagate trace context
}
```

**API note:** `ContextExecutorService.wrap(ExecutorService)` (single-arg)
is deprecated since 1.1.2 — must pass a `Supplier<ContextSnapshot>` as the
second argument. `ContextSnapshot.captureAll()` (static) is also deprecated
— use `ContextSnapshotFactory.builder().build()` and call `captureAll()` on
the factory instance.

**Result:** in Jaeger, all `getGameDetails` spans appear as children of the
parent `getTeamGamesParallel` span, starting at the same time — the parallel
fan-out is clearly visible in the trace timeline.

### OTLP Export: Dev vs Kind

The OTel OTLP exporter (uses OkHttp internally, separate from the JDK
`HttpClient` used for API calls) was logging `Connection refused` errors
locally when Jaeger was not port-forwarded.

**Fix:** `management.opentelemetry.tracing.export.enabled=false` by default
in `application-dev.properties`. The endpoint line is commented out to
prevent the exporter being initialised even if the flag is somehow bypassed.

In Kind, the Helm deployment sets both env vars when `otlpEndpoint` is
configured in values:
- `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_ENABLED=true`
- `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT=http://jaeger.observability:4318/v1/traces`

Kubernetes env var names must be C identifiers (`[A-Za-z_][A-Za-z0-9_]*`) —
dots are not valid. Spring Boot's relaxed binding maps the uppercase
underscore form to the dotted property name automatically; this is by design,
not a workaround.
