# 2026-03-28 — playground service

## Prometheus — Metrics Collection

### Architecture

Single Deployment pod in the `observability` namespace. Prometheus
scrapes metrics from pods on a 15s interval and stores time-series
data locally (emptyDir for dev, S3/object store in production).

```
Every 15s:
  Prometheus → Kubernetes API → discover pods with scrape=true annotation
  Prometheus → pod-ip:8080/actuator/prometheus → pull metrics
  Prometheus → store as time series (tsdb)

Grafana → http://prometheus.observability:9090 → query → dashboards
```

### RBAC

Prometheus needs ClusterRole to call the Kubernetes API for pod
discovery. Rules:
- `get/list/watch` on pods, nodes, services, endpoints, namespaces
  (core API group, `apiGroups: [""]`)
- `get` on `/metrics` nonResourceURL — allows scraping the
  kube-apiserver's own metrics endpoint

`apiGroups: ""` means the core Kubernetes API group (pods, nodes,
services). Other groups use explicit names: `apps`, `batch`,
`rbac.authorization.k8s.io`, etc.

### Pod annotation-based scrape discovery

Prometheus discovers scrape targets via pod annotations:

```yaml
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/path: /actuator/prometheus
  prometheus.io/port: "8080"
```

Kubernetes SD exposes annotations as `__meta_kubernetes_pod_annotation_*`
labels (dots and slashes → underscores). Relabel rules then:

1. **keep** — only pods with `prometheus_io_scrape=true`
2. **replace `__metrics_path__`** — override default `/metrics` with
   annotation value. `regex: (.+)` means only applies if annotation
   present.
3. **replace `__address__`** — rebuild `pod-ip:port` using annotation
   port. Regex `([^:]+)(?::\d+)?;(\d+)` captures IP ($1) and port
   ($2), discarding the existing port.
4. **attach labels** — `namespace`, `pod`, `app` become permanent
   metric labels for Grafana filtering.

### /actuator/prometheus format

Plain text OpenMetrics format. Each line:
```
metric_name{label="value"} numeric_value
# HELP metric_name description
# TYPE metric_name gauge|counter|summary|histogram
```

Naming convention: prefix = system (`jvm_`, `http_`, `cache_`),
suffix = unit + aggregation (`_bytes`, `_seconds_count`, `_total`).

### Metric types

| Suffix | Type | Meaning |
|---|---|---|
| `_total` | Counter | Always increasing, use `rate()` |
| `_bytes`, `_seconds` | Gauge | Current value |
| `_bucket` | Histogram | Distribution buckets for percentiles |
| `_count`, `_sum` | Summary parts | Count and total sum |

### How InstrumentedCache produces metrics

`InstrumentedCache` uses `ObservationRegistry` — one `obs.start()` /
`obs.stop()` call produces both a trace span AND Micrometer metrics
automatically. The observation name `cache.get` becomes
`cache_get_seconds_count/sum/max`. Tags set via
`lowCardinalityKeyValue()` become Prometheus labels. Tags set via
`highCardinalityKeyValue()` (e.g. cache key) go to traces only —
never Prometheus, to avoid cardinality explosion.

### Useful Prometheus queries

**RED method — the four most important:**
```promql
# Rate (RPS)
rate(http_server_requests_seconds_count{app="playground"}[1m])

# Errors
rate(http_server_requests_seconds_count{app="playground",status=~"5.."}[1m])

# Duration (p99)
histogram_quantile(0.99,
  sum by (pod, le) (rate(http_server_requests_seconds_bucket{app="playground"}[1m])))

# Heap utilization
sum by (pod) (jvm_memory_used_bytes{app="playground",area="heap"})
/ sum by (pod) (jvm_memory_max_bytes{app="playground",area="heap"})
```

**Cache hit ratio:**
```promql
rate(cache_get_seconds_count{app="playground",cache_result="hit"}[1m])
/ rate(cache_get_seconds_count{app="playground"}[1m])
```

**Per pod:** add `by (pod)` to `sum`/`avg` aggregations. For
histograms keep `by (pod, le)` — `le` is the bucket boundary label
required by `histogram_quantile`.

**Memory breakdown:** `jvm_memory_used_bytes` splits by `area` (heap,
nonheap) and `id` (Eden Space, Survivor Space, Tenured Gen, CodeHeap).
Values are in bytes — divide by `1048576` for MB or set Grafana panel
unit to "bytes (SI)".

## Access Log Filter — Structured HTTP Metrics via Loki

### Why a custom filter over Tomcat access log

Tomcat's built-in access log writes plain text Combined Log Format.
Querying it in Loki requires fragile regex extraction. A custom
`Filter` writing MDC fields lets `logstash-logback-encoder` emit them
as top-level JSON fields — queryable directly via `| json` in LogQL.

### Implementation

`AccessLogFilter` (`com.backyard.playground.filter`):
- `@Component` + `@Order(1)` — auto-registered by Spring Boot,
  runs first in the filter chain
- Wraps `chain.doFilter()` in try/finally — logs after response is
  committed so `status` is final, MDC always cleared even on exception
- Logs one INFO line in Tomcat Combined Log Format for local dev
  readability
- Sets 4 MDC fields before logging:
  `http.method`, `http.uri`, `http.status`, `http.duration_ms`

### How MDC becomes top-level JSON

SLF4J MDC is a `ThreadLocal<Map<String, String>>`. Any values set
in MDC are automatically included by `logstash-logback-encoder` as
top-level JSON fields in the log line — no explicit serialization
needed.

`logback-spring.xml` `!dev` profile lists them via
`<includeMdcKeyName>` — switching to whitelist mode. Only listed keys
are included; unlisted MDC keys are dropped.

### Kind profile

`application-dev.properties` activated the `dev` logback profile
(plain text) even in Kind pods, preventing JSON output. Added
`application-kind.properties` with Kind-specific config and changed
`values-kind.yaml` to `springProfile: kind`. The `!dev` logback
profile now activates for Kind pods → JSON output → Loki `| json`
works.

### LogQL queries

```
# Access log lines only
{app="playground"} | json | http_uri != ""

# Filter by URI pattern
{app="playground"} | json | http_uri =~ ".*/games.*"

# RPS
rate({app="playground"} | json | http_uri =~ ".*/games.*" [1m])

# Average latency (ms)
avg(avg_over_time(
  {app="playground"} | json | http_uri =~ ".*/games.*"
  | unwrap http_duration_ms [1m]))

# Per pod
avg by (pod) (avg_over_time(
  {app="playground"} | json | http_uri =~ ".*/games.*"
  | unwrap http_duration_ms [1m]))

# p99 latency
quantile_over_time(0.99,
  {app="playground"} | json | http_uri =~ ".*/games.*"
  | unwrap http_duration_ms [1m])
```

Note: Loki converts `.` to `_` in label names after `| json` parsing
— `http.uri` becomes `http_uri` in `by()` and `unwrap` clauses.

### Metrics vs logs for RPS/latency

| | Prometheus metrics | Loki log-based |
|---|---|---|
| RPS | `rate(counter[1m])` | `rate({...} \| json [1m])` |
| Latency | `histogram_quantile` from pre-aggregated buckets | `quantile_over_time` from raw values |
| Per URI breakdown | Only if `uri` label added at instrumentation time | Any field in the log line, ad-hoc |
| Cost | Cheap — pre-aggregated | Expensive — full scan at query time |
| Accuracy | Approximate (histogram buckets) | Exact (raw values) |

Metrics for dashboards and alerting. Logs for ad-hoc URI-level
analysis and debugging.

### Observability approaches for RPS/latency at scale

Three layers large teams use:

1. **Cloud LB metrics** (AWS ALB, GCP Load Balancer) — external view,
   no cluster setup needed
2. **Service mesh** (Istio/Envoy sidecar) — per-service metrics
   without app instrumentation, standard metric names
3. **Micrometer** (app-level) — JVM internals, cache, DB pools,
   custom business metrics

All three feed into Prometheus → Grafana.

## Dory Reminders API — Migration from Node.js

Migrated the dory-server (Node.js/Express + flat JSON file) into the
playground Spring Boot service. Full CRUD for personal reminders with
JPA-backed H2 persistence.

### Why H2 over raw JSON file

Considered keeping file-based JSON (mirrors dory-server exactly), but
chose H2 file-based + JPA for:
- Concurrency safety (no race conditions on concurrent writes)
- SQL querying and proper indexes
- Easy upgrade path to PostgreSQL (one config line change)
- Free CRUD via `JpaRepository` — no manual read/write/find logic

### ORM stack: Hibernate vs DataNucleus

**Hibernate** chosen over DataNucleus:
- Better Spring Boot integration (zero-config auto-setup)
- Much larger community and Stack Overflow coverage
- DataNucleus's main advantage is multi-store support
  (MongoDB, HBase, Cassandra, Excel, LDAP) — irrelevant here
- DataNucleus is niche; used mainly in Google App Engine and
  Apache Hive metastore

Key Hibernate concepts discussed:
- **Lazy loading** — related entities loaded on first access, not at
  query time. Avoids unnecessary DB calls but risks N+1 if used in loops
- **N+1 query problem** — loading a list then accessing a lazy relation
  on each item fires 1 + N queries. Fix with `JOIN FETCH` in `@Query`
- **Bytecode enhancement** — DataNucleus default; modifies compiled
  `.class` files to inject tracking directly. Faster than Hibernate's
  runtime proxy approach, but requires a build step
- **First-level cache** — per-Session (per-request), always on. Same
  `findById()` in one request hits DB once. Destroyed when request ends
- **Second-level cache** — cross-request, opt-in. Shared across
  sessions; requires distributed cache (Redis) in multi-pod deployments
  to avoid stale data between pods

### Schema design decisions

Single `reminder` table — one-to-one mapping, no joins needed:

| Column | Notes |
|--------|-------|
| `id` | UUID primary key |
| `owner` | VARCHAR — query param for now, auth header later |
| `title`, `type`, `description` | Core fields |
| `recurrence_type` | Enum: DAILY/WEEKLY/MONTHLY/YEARLY, null for one-off |
| `next_occurrence` | TIMESTAMP WITH TIME ZONE |
| `snooze_until` | Nullable — stacks from current value, not from now |
| `status` | Enum: LIVE/DONE |
| `completed_at` | Nullable — set server-side when marked done |

Composite index `(owner, status)` — low cardinality on `status` alone
makes a single-column index useless; owner narrows to high selectivity
first. Annotation: `@Index(columnList = "owner, status")` on `@Table`.

`recurrence` object from dory-server JSON (`{ "interval": "weekly" }`)
flattened to single column `recurrence_type` — simpler schema, no join,
reconstructed in `ReminderResponse.from()`.

### API endpoints

All at `/api/{version}/dory/reminders` (prefix added by `WebMvcConfig`):

| Method | Path | Notes |
|--------|------|-------|
| GET | `?owner=&status=LIVE` | status defaults to LIVE |
| POST | `?owner=` | server generates UUID |
| PUT | `/{id}` | update content fields only |
| PATCH | `/{id}/done` | one-off: status=DONE; recurring: advance nextOccurrence |
| PATCH | `/{id}/snooze?minutes=N` | base = snoozeUntil ?? nextOccurrence |
| DELETE | `/{id}` | hard delete, 204 |

Recurring `markDone` is server-side — server reads `recurrenceType` and
advances `nextOccurrence` by the correct interval using
`java.time.ZoneOffset.UTC` for month/year arithmetic (avoids DST bugs).

Snooze stacks: `snoozeUntil = (snoozeUntil ?? nextOccurrence) + N min`.
Repeated snoozes keep pushing further from the last snoozed time.

### JPA / Spring Data notes

- `JpaRepository` — Spring generates SQL from method names at startup.
  `findByOwnerAndStatus` → `WHERE owner = ? AND status = ?`. No SQL
  written manually for standard CRUD
- `@Transactional` on all writes — read + write atomic, rolled back
  together if anything throws. `@Transactional(readOnly=true)` on reads
  skips Hibernate dirty checking (minor perf benefit)
- `@Enumerated(EnumType.STRING)` — stores `"LIVE"/"DONE"` as readable
  strings in DB column, not integer ordinals
- `ddl-auto=update` — Hibernate adds new columns on restart, never
  drops. Suitable for personal tool; use Flyway/Liquibase for prod
- `Instant` serializes as ISO 8601 string (`"2026-03-29T09:00:00Z"`) in
  Jackson 3 (Spring Boot 4) by default — no config needed. The
  `write-dates-as-timestamps` property was removed in Jackson 3

## Spring Profile Refactor

### Goal

Remove environment-specific properties files from the repo. All
Kind/stage/prod config injected at runtime via Helm env vars.

### Before

```
application.properties          base
application-dev.properties      local dev
application-kind.properties     Kind cluster (redundant with Helm)
```

### After

```
application.properties          base — all values ${ENV_VAR:default}
application-dev.properties      local dev — hardcoded values
application-home.properties     home jar — no Redis, no tracing
```

`application-kind.properties` deleted — every setting was already
covered by Helm env vars.

### 12-factor pattern

- Base properties = contract of what the app needs, `${ENV_VAR:default}`
- Dev properties = convenience layer, no env vars needed locally
- Helm = actual values per environment, injected at pod start
- GitHub Actions builds the jar with no profile — image is agnostic

### home profile

Long-running pre-built jar on local network. Serves dory APIs only.
No Redis, no tracing, no Prometheus endpoint. INFO-level plain text logs
(readable in pm2). Port 3100, H2 at `~/.backyard/dory-home.mv.db`.

Two gatekeepers required to fully disable Redis:
1. `@Profile("!home")` on `CacheConfig` — skips your Redis `@Bean`
   declarations
2. `spring.autoconfigure.exclude` in `application-home.properties` —
   skips Spring Boot's own Redis autoconfiguration (runs independently
   of your config classes because the jar is on the classpath)

`CacheConfigForHomeProfile` routes all cache types (LOCAL, DISTRIBUTED,
MULTI_LEVEL) to Caffeine. `HomeCacheConfig` was the original name,
renamed to `CacheConfigForHomeProfile` for clarity.

OTLP tracing: setting `management.opentelemetry.tracing.export.otlp
.endpoint` to an empty string `""` causes startup failure ("Invalid
endpoint"). Fix: remove the property from base — Spring Boot picks up
the env var directly via its property binding convention
(`MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT` →
`management.opentelemetry.tracing.export.otlp.endpoint`). When the env
var is absent the property is simply unset; Spring Boot uses a valid
default URL that doesn't crash at startup.

### Logback profile matrix

| Profile | Format | Level |
|---------|--------|-------|
| `dev` | Plain text | DEBUG |
| `home` | Plain text | INFO |
| `!dev & !home` | JSON (Logstash) | INFO |

`!dev,!home` (comma = OR) was a bug — both `dev` and JSON blocks fired
simultaneously causing duplicate log output. Fixed using nested
`<springProfile>` blocks (AND semantics, no XML escaping needed).
`&amp;` syntax also works but requires XML escaping.

### H2 file paths

| Environment | DB file |
|-------------|---------|
| `dev` | `~/.backyard/dory-dev.mv.db` |
| `home` | `~/.backyard/dory-home.mv.db` |
| Kind pod | `~/.backyard/dory-kind.mv.db` (hostPath PV at `/data`) |

Separate files per environment prevent H2 file locking conflicts when
multiple instances run simultaneously.

### Scripts

```
scripts/run-service-playground-dev.sh    mvn spring-boot:run --dev
scripts/build-service-playground-home.sh  package + copy to ~/.backyard/bin/
scripts/run-service-playground-home.sh    java -jar from ~/.backyard/bin/
```

`~/.backyard/bin/playground.jar` survives `mvn clean` — stable jar
for home profile unaffected by active development builds.
