## Scaling Parallel I/O with Virtual Threads

### 1. The Core Mechanism: Virtual Threads (Project Loom)

**The benefit:** Virtual threads are lightweight (KB vs MB for platform
threads) and live on the heap. They allow effectively unbounded concurrency
for I/O-bound tasks without exhausting OS thread limits.

**The magic:** When `restClient.get()` blocks waiting for a network response,
the JVM unmounts the virtual thread from its carrier (platform) thread. The
carrier thread is freed to run other virtual threads. When the OS signals that
data has arrived, the virtual thread is remounted and continues — the blocking
call returns as if nothing happened.

**The trap:** Virtual threads solve the thread bottleneck but they do not
solve the resource bottleneck. Downstream systems (databases, external APIs)
have their own limits — connection pool sizes, rate limits, QPS caps. Use a
`Semaphore` to protect downstream systems when fan-out concurrency is high:

```java
Semaphore semaphore = new Semaphore(20); // max 20 concurrent outbound calls
executor.submit(() -> {
    semaphore.acquire();
    try {
        return client.getGameDetails(id);
    } finally {
        semaphore.release();
    }
});
```

---

### 2. The Infrastructure: HTTP & Connection Pooling

**HTTP/1.1 constraints:** Each request requires a dedicated TCP connection.
If the connection pool is capped at 20, the 21st virtual thread blocks in Java
waiting for a connection to become free — it never reaches the network and
never unmounts from the carrier thread. The parallelism benefit is lost.

**The HTTP/2 advantage:** Multiplexing allows hundreds of concurrent requests
over a single TCP connection as independent streams. All virtual threads can
send their requests and unmount immediately without waiting for a free
connection — the full concurrency benefit is realised.

**Pool sizing rule for HTTP/1.1:**
```
MaxTotal connections ≥ expected peak concurrency (RPS × avg latency)
```
Example: 100 RPS, 200ms average latency → at any instant ~20 requests
in-flight → pool needs at least 20 connections.

---

### 3. The Architecture: Edge vs. Internal Services

**Edge termination in production (GKE/AWS):** The Ingress/Gateway handles
the hard parts — TLS termination and HTTP/2. It speaks HTTP/2 to the client
and translates to HTTP/1.1 for internal pods. Internal service code requires
no changes to benefit from HTTP/2 at the edge.

**Local dev with Kind:** To test HTTP/2 end-to-end locally, a self-signed
certificate for `localhost` is required. Browsers and `curl` refuse to
negotiate HTTP/2 over plain text (h2c) by default — they require TLS for h2.

**Service impact:** Internal services typically don't need to change for
HTTP/2 support. The Ingress acts as the protocol translator — pods see
plain HTTP/1.1, clients see HTTP/2.

---

### 4. Bottleneck Analysis & Observability

**Backpressure:** If the service is slow to respond, HTTP/2 flow control
eventually throttles the Ingress, which in turn throttles the client. The
pressure propagates upstream automatically — no requests are silently dropped.

**Tracing:** Use `ContextExecutorService.wrap()` (Micrometer) when submitting
to virtual thread executors. Without it, trace context (`ThreadLocal`) is not
copied to child threads and spans appear disconnected in Jaeger.

**Signs of trouble:**

| Symptom | Likely Cause |
|---|---|
| Staircase pattern in Jaeger (spans start sequentially, not in parallel) | Connection pool too small — virtual threads are queuing for a connection |
| High Ingress CPU, low Pod CPU | HTTP/2 framing/compression overhead at the gateway |
| Spans missing parent in Jaeger | `ContextExecutorService.wrap()` not used on the executor |

## RxJava vs Virtual Threads — Parallel Fan-out

### RxJava thread model

By default RxJava is single-threaded — everything runs on the thread that
called `subscribe()`. Two operators control threading:

- **`subscribeOn(scheduler)`** — which thread runs the upstream source work
- **`observeOn(scheduler)`** — which thread runs downstream operators and
  the final callback

### Schedulers

| Scheduler | Backed by | Use for |
|---|---|---|
| `Schedulers.io()` | Unbounded cached pool, threads expire after 60s idle | HTTP calls, DB queries, file I/O |
| `Schedulers.computation()` | Fixed pool, size = CPU core count | CPU-bound work: parsing, math, transformation |
| `Schedulers.newThread()` | New thread per task, never reused | Rare — isolated long-running tasks |
| `Schedulers.single()` | Single background thread, tasks queue sequentially | Operations that must not run concurrently |
| `Schedulers.trampoline()` | Current thread, FIFO queue | Tests — makes async code run synchronously |

### Fan-out pattern

Starting from an already-fetched list, firing parallel detail calls per item:

```java
// games already fetched (blocking call done)
List<Game> games = client.getTeamGames(teamId);

List<Game> details = Observable.fromIterable(games)  // Observable<Game> — emits each item
    .flatMap(g ->
        client.getGameDetails(g.gameId())  // Observable<Game> per item
            .subscribeOn(Schedulers.io())  // each call gets its own io() thread → parallel
    )
    .toList()       // collect all emissions into Single<List<Game>>
    .blockingGet(); // triggers the whole pipeline, blocks until all done
```

**`Observable.fromIterable(games)`** returns `Observable<Game>` — unwraps
the list into individual emissions, one per element. Compare with
`Observable.just(games)` which gives `Observable<List<Game>>` — one emission
of the whole list.

**`flatMap` vs `map`:** `map` transforms each item into a plain value.
`flatMap` transforms each item into an `Observable` and merges all those
inner observables into one stream — this is what enables concurrent
subscriptions. Each inner `subscribeOn` dispatches to its own `io()` thread
so all calls run in parallel.

**`blockingGet()`** is the only line that triggers execution — all operators
above are lazy descriptions. It subscribes to the pipeline, starts all work,
and blocks the calling thread until `toList()` has collected every result.

### Compared to virtual threads

```java
// RxJava
Observable.fromIterable(games)
    .flatMap(g -> client.getGameDetails(g.gameId())
            .subscribeOn(Schedulers.io()))
    .toList()
    .blockingGet();

// Virtual threads
try (ExecutorService executor = ContextExecutorService.wrap(
        Executors.newVirtualThreadPerTaskExecutor(),
        contextSnapshotFactory::captureAll)) {
    games.stream()
        .map(g -> executor.submit(() -> client.getGameDetails(g.gameId())))
        .toList();
    // collect via Future.get()...
}
```

Same parallelism and same blocking behaviour at the end. RxJava requires
explicit scheduler wiring on every nested observable — easy to forget one
and accidentally serialize all calls. Virtual threads just submit and the
JVM handles the rest.
